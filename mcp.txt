# MCP (Model Context Protocol)

-- A standardized protocol that allows AI applications to
interact with external tools, resources, and services.

-- MCP servers expose capabilities.

-- MCP clients connect AI applications to those capabilities.

-- Mental model:
MCP is like a standardized API/interface designed
specifically for AI-to-tool/service interaction.

# MCP ARCHITECTURE

```text
                    AI Application / Host
                           │
                    ┌──────┴──────┐
                    │ MCP Client  │
                    └──────┬──────┘
                           │
                    MCP Protocol
                    (JSON-RPC 2.0)
                           │
                    ┌──────┴──────┐
                    │ MCP Server  │
                    └──────┬──────┘
                           │
              ┌────────────┼────────────┐
              ↓            ↓            ↓
            Tools       Resources     Prompts
              │            │            │
              ↓            ↓            ↓
          Actions        Data        Templates
```

-- Host / AI Application:
The application containing or using the LLM.

Examples:
Claude Desktop
A custom LangChain application

-- MCP Client:
The component that manages the MCP connection
between the AI application and an MCP server.

-- MCP Server:
A program that exposes capabilities through MCP.

-- Important:
The LLM does not directly establish the MCP connection.
The host/application mediates communication through
the MCP client.

# MCP STANDARDIZATION

-- Before MCP:

Different APIs/services had their own interfaces,
input/output formats, tool definitions, and
interaction patterns.

-- MCP:

Provides a standardized protocol for AI applications
to discover and interact with external tools, resources,
and services.

-- MCP does NOT make every tool use the same inputs.

-- Each tool can have its own schema based on its
functionality.

-- MCP standardizes HOW the AI application communicates
with and uses those capabilities.

-- Mental model:

MCP is like a standardized interface/protocol
designed for AI-to-tool/service interaction.

# MCP SERVER COMPONENTS:

# TOOLS, RESOURCES & PROMPTS

## Tools

-- Actions/functions that an AI application can invoke
through an MCP server to perform an operation.

-- Examples:

Create a GitHub issue
Send an email
Query a database
Read or modify a file

-- Mental model:

Tool → Do something / perform an action

## Resources

-- Data/context that an AI application can access
through an MCP server.

-- Examples:

Files
Database records
Documentation
Application data

-- Resources are generally intended to provide data/context
rather than perform an action.

-- Mental model:

Resource → Give me data/information

## Prompts

-- Predefined/reusable instructions or templates
exposed by an MCP server for an AI application.

-- They provide guidance for performing a particular task.

-- The MCP client/host retrieves the prompt from the
MCP server and makes it available to the application/LLM.

-- The LLM does not directly establish an MCP connection.

-- Mental model:

Prompt → Guide the AI

## Simple Mental Model

```text
Tool      → Do something
Resource  → Give me data
Prompt    → Guide the AI
```

# MCP TOOL SCHEMAS

-- An MCP tool generally provides:

name
description
input schema

-- The input schema describes what arguments the tool accepts.

-- Example:

Tool:
name: add
description: Add two numbers

```
   input:
       x → number
       y → number
```

-- The LLM/application can use the tool definition
to understand how the tool should be called.

# TOOL DISCOVERY

-- MCP allows clients to discover capabilities exposed
by an MCP server.

-- The client can ask the server what tools, resources,
and prompts are available.

-- Mental model:

Discovery → What can you do?
Invocation → Do this operation.

-- Example:

```text
Client → MCP Server
        "What tools do you provide?"

Server → Client
        add
        subtract
        multiply
        divide
        modulus
        square_root
```

-- This allows the client/application to discover
capabilities instead of hardcoding every capability
into the client.

# MCP LIFECYCLE

-- Client establishes a connection with the MCP server.

-- Client and server initialize the MCP session.

-- Client discovers the server's available capabilities.

-- The application makes relevant tools, resources,
and prompts available to the LLM.

-- The LLM determines when a capability is needed.

-- The host/client sends the appropriate MCP request.

-- The MCP server performs the operation.

-- The server returns the result to the client.

-- The application provides the result back to the LLM
so it can continue processing.

# URI vs URL

-- URI:
Identifies a resource.

-- URL:
A URI that also specifies where/how the resource
can be accessed.

-- Mental model:

URI → What resource?
URL → What resource + where/how to access it?

# JSON-RPC 2.0

-- JSON-RPC 2.0 is a lightweight protocol for making
remote procedure calls using JSON.

-- It defines a standardized structure for communication
between a client and server.

## Request

-- A request generally contains:

jsonrpc → protocol version
method  → operation to perform
params  → arguments for the operation
id      → identifies the request

-- Example:

```json
{
  "jsonrpc": "2.0",
  "method": "get_user",
  "params": {
    "id": 10
  },
  "id": 1
}
```

-- The server processes the request and returns
a response.

## Response

-- Successful response contains:

result → successful result
id     → matches the original request

-- Failed response contains:

error  → error information
id     → matches the original request

-- MCP uses JSON-RPC 2.0 as the messaging format
between MCP clients and MCP servers.

-- Mental model:

JSON-RPC → standardized structure for
"request something → receive a response"

## Notification

-- A notification is a message that does not require
a response.

-- Unlike a request, it does not contain a request ID.

-- Useful for informing the other side that something
happened or changed.

# TRANSPORT

-- Transport defines HOW messages are exchanged
between an MCP client and MCP server.

## stdio

-- Client and server communicate through standard
input/output.

-- Common when the MCP server runs as a local process.

-- Example:

```text
Claude / LangChain
       │
      stdio
       │
       ↓
FastMCP Server
```

## Streamable HTTP

-- Client and server communicate over HTTP.

-- Useful when the MCP server runs as a network service
or remote service.

# LOCAL vs REMOTE MCP

## Local MCP

-- MCP server runs as a local process.

-- Example:

```text
Claude Desktop
      │
    stdio
      │
      ↓
Local FastMCP Server
```

## Remote MCP

-- MCP server runs as a network service.

-- Example:

```text
AI Application
      │
    HTTP
      │
      ↓
Remote MCP Server
```

# MCP CLIENT CAPABILITIES

-- MCP clients can provide capabilities that allow
servers to interact with the host/application.

## Roots

-- Define filesystem locations that the MCP client/host
makes available to an MCP server.

-- They can communicate which directories are relevant
or permitted for the server to work with.

-- Example:

A shared project folder.

-- Mental model:

Roots → Where can the server work?

## Sampling

-- Allows an MCP server to request an LLM completion
from the MCP client/host.

-- The client/host controls which LLM is used and
whether the request is allowed.

-- Mental model:

Sampling → Ask the host's LLM to generate something.

## Elicitation

-- Allows an MCP server to request additional information
from the user through the MCP client.

-- Example:

Asking the user for a missing value
Asking the user to confirm an action

-- Mental model:

Elicitation → Ask the user for information.

## Simple Mental Model

```text
Roots       → Where can the server work?
Sampling    → Ask the LLM to generate something
Elicitation → Ask the user for information
```

# MCP REQUEST FLOW

-- Example: User asks an AI:

"Calculate the square root of 25."

```text
User
 ↓
AI Application / Host
 ↓
LLM decides a math tool is needed
 ↓
MCP Client
 ↓
MCP Server
 ↓
square_root(25)
 ↓
Result: 5
 ↓
MCP Client
 ↓
AI Application / LLM
 ↓
User receives answer
```

-- The important point:

The LLM decides what capability is needed,
while the host/client handles the actual MCP communication.

# CLAUDE AND LANGCHAIN AS MCP CLIENTS

## Claude Desktop

-- Claude Desktop acts as the AI application/host.

-- It can use MCP clients to connect to configured
MCP servers.

-- Example:

```text
Claude Desktop
      │
   MCP Client
      │
    stdio
      │
      ↓
Math MCP Server
```

## LangChain

-- A LangChain application can act as an MCP client.

-- `MultiServerMCPClient` can connect to multiple
MCP servers.

-- Example:

```text
LangChain Application
        │
MultiServerMCPClient
        │
   ┌────┴────┐
   ↓         ↓

```

-- The MCP server does not need to know whether its
client is Claude, LangChain, or another MCP-compatible
application.

# MCP SERVER CONFIGURATION

-- A client needs configuration describing how to
connect to an MCP server.

-- Example using LangChain:

```python
SERVERS = {
    "math": {
        "transport": "stdio",
        "command": "/path/to/uv",
        "args": [
            "run",
            "fastmcp",
            "run",
            "src/math_mcp_server/main.py"
        ],
        "cwd": "/path/to/math-mcp-server"
    }
}
```

-- `transport`:
Defines the communication mechanism.

-- `command`:
Program used to start the MCP server.

-- `args`:
Arguments passed to the command.

-- `cwd`:
Working directory in which the server is started.

-- With Claude Desktop, the server is configured in
Claude's MCP configuration rather than through
`MultiServerMCPClient`.

# ADVANCED / RECENT MCP CONCEPTS

## Stateless Servers

-- MCP servers can be designed so that requests do not
depend on server-side session state.

-- Stateless architectures make horizontal scaling
and load balancing easier.

-- Example:

```text
              Load Balancer
              /     |     \
             ↓      ↓      ↓
          Server  Server  Server
             1      2       3
```

-- Benefits:

Better scalability
Higher availability
Easier horizontal scaling
Simpler operations

## Tasks

-- Used for operations whose results may not be immediately
available.

-- Useful for longer-running or asynchronous operations.

-- Allows an operation to be represented as a task whose
result can become available later.

## Elicitation in Long-Running Operations

-- A server may need additional information from the user
before continuing.

-- The server can request that information through the
client.

-- The operation can then continue after the user responds.

-- In a scalable architecture, application design can avoid
requiring one server instance to remain blocked while
waiting for user input.

## MCP Apps

-- MCP Apps allow MCP servers to provide interactive
user interfaces alongside tool functionality.

-- This allows MCP interactions to go beyond plain
text/tool results and provide richer UI experiences.

## Caching

-- Stores previously generated or retrieved results so
they can potentially be reused.

-- TTL (Time To Live):
How long a cached result remains valid.

-- Cache scope:
Determines who can reuse the cached result.

-- Benefits:

Less server/LLM load
Faster responses
Lower cost

## Tracing

-- Distributed tracing tracks a request across the
different components involved in processing it.

-- W3C Trace Context uses headers such as:

traceparent
tracestate

-- Helps provide:

End-to-end visibility
Faster debugging
Easier identification of bottlenecks/failures

## Security

-- MCP implementations need to consider:

Authentication
Authorization
User consent
Data access
Tool execution safety
Input validation

-- Important:

An MCP tool can potentially perform real-world actions,
so tool access should be treated as a security boundary.

-- MCP SDK provides the core building blocks for

-- It provides APIs for:

MCP servers
MCP clients
MCP protocol communication
MCP CLI/development tooling

-- Python installation:

```bash
pip install "mcp[cli]"
```

-- The lower-level SDK can involve more protocol-level
code and boilerplate.

# FastMCP

-- FastMCP provides a higher-level abstraction for
building MCP applications.

-- It makes MCP server development simpler and faster.

-- Example:

```python
from fastmcp import FastMCP

mcp = FastMCP("math-server")

@mcp.tool()
async def add(x, y):
    return x + y
```

-- `@mcp.tool()` exposes the Python function as
an MCP tool.

-- Installation:

```bash
pip install fastmcp
```

-- FastMCP can be used for both MCP server and
client development.

# BASIC MCP SERVER EXAMPLE

```python
from fastmcp import FastMCP

mcp = FastMCP("math-mcp-server")


@mcp.tool()
async def add(x, y):
    """Add two numbers."""
    return x + y


@mcp.tool()
async def square_root(x):
    """Calculate the square root of a number."""
    return x ** 0.5


if __name__ == "__main__":
    mcp.run()
```

-- `FastMCP()`:
Creates the MCP server.

-- `@mcp.tool()`:
Exposes a Python function as an MCP tool.

-- `async def`:
Defines an asynchronous Python function.

-- `**`:
Exponentiation / power operator.

-- `** 2`:
Square.

-- `** 0.5`:
Square root.

# HELPER FUNCTIONS IN MCP TOOLS

-- MCP tools often use helper functions to validate
or convert their inputs.

-- Example:

```python
def _as_number(x):

    if isinstance(x, (int, float)):
        return x

    if isinstance(x, str):
        return float(x.strip())

    raise TypeError(
        f"Expected int, float, or numeric string, "
        f"got {type(x).__name__}"
    )
```

-- `_as_number()` is NOT a Python built-in.

-- It is a custom helper function.

-- `isinstance()` checks the type of a value.

-- `float()` converts a numeric string into a floating-point
number.

-- `strip()` removes surrounding whitespace.

-- `TypeError` is raised when the input type is unsupported.

-- The leading `_` is a naming convention commonly used
for helper/internal functions.
